## The command reference

`/reference` renders the toolchain's own command reference, generated by
`sigil reference` and committed to `src/reference/`. Refresh it with:

```sh
pnpm --filter @ttylabs/cli reference
```

`src/lib/reference.ts` reads the directory, parses the YAML front matter --
whose values are JSON, so no YAML parser is needed to read three keys -- and
builds the nav from `title` and `path`. `packages/cli/test/command-surface.test.ts`
fails if the committed pages are not what the toolchain's own schema says, and
if a page stops being one this can read.

Generated and committed rather than written during `next build`, which is the
call `packages/sigil/src/i18n/keys.ts` already makes: a generated file in the
tree is one a reviewer can read in the diff, and a drift test is what keeps it
honest -- where generating at build time would make this build depend on
importing the toolchain's own app.

How a page is drawn is the site's business rather than the generator's, so the
committed markdown stays what GitHub shows. `src/lib/reference-blocks.ts` makes
the untagged fence under `## Usage` a terminal block with no working directory
in its title bar (an `sh` fence with `cwd=""`, which a guide can write too), and
marks the name and `Type` columns of the argument, option and command tables,
which `globals.css` sets in the mono face and in `syn-keyword`. The index's
introduction and its install box are in `src/components/reference-page.tsx`,
since the generator documents commands and has no place for them.

## The docs layout

`/docs/[slug]` renders the guides in `packages/sigil/docs/` in place (they are
not copied: `packages/cli/test/guides.test.ts` and `markdown-links.test.ts` read
the originals, and `turbo.json` lists them as build inputs). The command
reference is in the same layout. Both are in the `(sidebar)` route group, whose
layout is the sidebar; a page renders its content and its "On this page" rail
(`src/components/docs-page.tsx`), and a docs page with no sidebar of its own
goes outside the group.

- `src/lib/nav.ts` is the one definition of the sidebar (`sidebarSections()`),
  of which guides there are and in what order (`GUIDE_SLUGS`), and of the
  Previous and Next cards (`pagerAround()`, within a section).
- A heading's anchor is the slug GitHub gives it (`src/lib/markdown-doc.ts`),
  because the guides link to themselves with fragments only GitHub's rule has
  to satisfy. `test/guides.test.ts` follows every link in them: one to a sibling
  guide becomes its route, one to anything else in the repository becomes that
  file on GitHub (`src/lib/guide-links.ts`).
- The parser reference is one page. Its 17 sections cross-link by fragment, the
  link test checks them against one file's headings, and the rail is the
  navigation a split would have needed.
- `/docs/about` (SIG-266) is `docs/about.md` at the repository's root, beside
  the `docs/history/` it links to, and not in `packages/sigil/docs/`, which is
  the Docs section's reading order. It is read by the guides' reader
  (`about()` in `src/lib/guides.ts`, and `markdownPages()` for every markdown
  page under `/docs/`) but has a route of its own, because it has no place in
  that order and no Previous or Next. Its relative links resolve from `docs/`.
- A block the plain renderer cannot draw is named by a comment on the line
  before it, `<!-- as timeline -->`, `<!-- as points -->` or
  `<!-- as github -->` (`src/lib/block-styles.ts`), so the page is still plain
  markdown on GitHub and in a `.md` copy. A name it does not know, or a block of
  the wrong shape, fails the build.

## Brand assets

The seal's geometry is `src/lib/seal.ts` and the `Seal` component draws it
(`src/components/seal.tsx`). Everything else is generated from it by
`pnpm --filter website brand`: `src/app/icon.svg`, `src/app/favicon.ico`
(16, 32 and 48 px), `src/app/apple-icon.png`, `public/icon-192.png`,
`public/icon-512.png`, and the lockups in `public/brand/`, which have the
wordmark outlined into paths so they need no font:

- `public/brand/sigil-lockup-dark.svg`: for a dark ground
- `public/brand/sigil-lockup-light.svg`: for a light one

The PNG and ICO files are stamped cell by cell rather than rendered from the
SVG, so a 16 px favicon keeps its channel open instead of blurring it shut.
`test/brand-assets.test.ts` regenerates all of them in memory and fails if a
committed file differs, so editing the seal without running the script is a
test failure. The social cards are `src/lib/og.tsx`; each route's
`opengraph-image.tsx` is a call into it and exports its own `alt`: Next reads
an `.alt.txt` only beside a static image, and a route that read one by a
computed path would make Turbopack trace the whole project. `next/og` cannot read woff2, so `src/lib/woff2.ts` decodes
the vendored fonts for it.

## Code and terminal blocks

A fenced block in any markdown the site renders goes through
`src/components/markdown-blocks.tsx`: ` ```console ` and ` ```sh `
become a `TerminalBlock`, anything else a `CodeBlock`, highlighted by Shiki at
build time with a theme that names the `--color-syn-*` tokens rather than
copying them. `> [!NOTE]` becomes a callout.

A terminal's colour is the program's own where it can be. A ` ```console `
run whose text matches a capture in `src/transcripts/` is drawn from the escape
sequences that command really printed, parsed by `@ttylabs/sigil`; anything
else is coloured by its leading glyph. The captures are the guides in
`packages/sigil/docs/`, replayed with colour forced, and are committed.
`test/transcripts.test.ts` fails when a guide has moved on; refresh them with:

```sh
node scripts/capture-transcripts.ts
```

That needs `@ttylabs/sigil` built, and so does this site's build, which now
depends on it -- turbo builds it first.

The same command captures the components pages. Each component has an example
in `src/content/components/<slug>.mjs`, ordinary app code that the page shows as
its source; `scripts/lib/run-example.mjs` runs it on a faked terminal with a fake
clock, so the frame it keeps is the same on every machine, and the result goes
to `src/transcripts/components/` with the options read off the built
declarations. A component's page shows it three ways (80 columns, accessible,
40 columns), and its Keys are what its key-help footer lists plus what pressing
each key on the running example was seen to do. `test/component-captures.test.ts` fails when one has gone stale.
The list of components is `src/lib/components.ts`, and
`test/components.test.ts` fails on an export of `@ttylabs/sigil/components`
that is neither a component there nor a helper with a reason.

## Metadata, sitemap and robots.txt

`src/lib/site.ts` is where the site's name, its production URL (`SITE_URL`),
the repository and the tagline live, and `isIndexableHost()`. Nothing else
spells the domain, so settling it (SIG-271) is a one-line change there.
`SITE_URL` is a placeholder until then. A request is indexable only when its
`Host` is the production host: previews, `*.vercel.app` URLs and `localhost`
get `Disallow: /` from `robots.txt` and a 404 for `/sitemap.xml` (`src/proxy.ts`).
That is a per-request question, unlike `isProductionDeploy()`, which asks at
build time whether this build is the production deployment.

`src/lib/seo.ts` has what every route shares: `pageMetadata()` gives a page its
canonical, Open Graph and Twitter fields from one title and description, and a
route that sets `openGraph` must go through it, because metadata replaces a
parent's object rather than merging into it (a route that does so also needs an
`opengraph-image` of its own, as `reference/[slug]` has). `src/lib/sitemap.ts`
lists the pages as sections; a new part of the site adds a function and a line
to `SECTIONS`. `lastModified` comes from git and is left out in a shallow clone,
where every file would claim the deploy's own date.

## Search

Ported from titaniumsdk.com, in two halves. `src/lib/search-records.ts` builds
one record per command, per option and per guide section from the same markdown
the pages render, with one function per source in `SOURCES`; a new part of the
site is one more function there. Two generators run before `next build`:

```sh
pnpm --filter website search:index    # Pagefind, into public/_pagefind/
pnpm --filter website search:symbols  # the name matcher's public/symbols.json
```

Pagefind answers prose. The name matcher (`src/components/search/symbols.ts`)
answers names, including misspelt ones, through `nearMiss()` from
`@ttylabs/sigil/suggest`, so the site corrects `--singel` the way the CLI does.
Its file has a 40 KB brotli budget, enforced by the generator. The dialog is
`src/components/search/site-search.tsx`, mounted once in the root layout and
opened by `openSearch()`, ⌘K, Ctrl+K or `/`. An option's row on a reference page
is its own anchor (`/reference/build#--out`), which is where its result lands.

Both outputs are gitignored. `turbo.json` excludes them from the build's
`inputs`, because an explicit `inputs` list hashes gitignored files and the
build would otherwise move its own hash, and lists them in `outputs`, so a cache
hit restores them with `.next/`. `next dev` does not run the generators; run
them once for search to work there.

## Markdown copies, `llms.txt` and `llms-full.txt`

Ported from titaniumsdk.com (TI-57). Every docs page has a Markdown copy at its
own address plus `.md` -- `/docs/parser.md`, `/docs/components/select.md`,
`/reference.md`, `/reference/add.md` -- and the page's own address answers with
it when the request's `Accept` prefers `text/markdown`. Each page's head names
its copy with `<link rel="alternate" type="text/markdown">` (`pageMetadata()`).
`/llms.txt` is the index, to the llmstxt.org convention, and `/llms-full.txt` is
every page concatenated, both in the docs sidebar's order.

- `src/lib/docs-pages.ts` is the one loader of the docs as Markdown, and search
  (`search-records.ts`) reads the guides and the reference through it too. A
  guide and a command page are their own source; a component page is written
  out from its capture with the words its page uses (`component-text.ts`): the
  output as ` ```console ` blocks without colour, the options and keys as GFM
  tables. `/docs/<slug>` comes from `markdownPages()` in `guides.ts`, so a
  markdown page added there -- About, with SIG-266 -- has a copy and an entry in
  `llms.txt` with nothing else to change.
- `src/lib/llms.ts` turns a page into its file: a first line naming the version
  (`<!-- sigil v0.0.1 · https://.../docs/parser -->`, from
  `packages/sigil/package.json`) and every link absolute, a docs page's to its
  `.md`.
- A `route.ts` cannot share a segment with a `page.tsx`, so `next.config.ts`
  rewrites the `.md` suffix onto `app/md/[...path]`, and `src/proxy.ts` refuses
  `/md/...` asked for by name and negotiates on `Accept`. That keeps every one
  of those routes prerendered.
- The corpus is served on every host, previews and `localhost` included, unlike
  titaniumsdk.com's. It is the same documents every host serves as HTML, so a
  host guard hid nothing and only made it untestable off production. Only the
  sitemap is production-only, because it claims the canonical addresses.
- A Markdown answer says `Vary: Accept`. The HTML page cannot: Next sets a
  page's `Vary` outright, over anything the proxy or `next.config.ts` adds, so a
  cache can at worst give an agent the HTML, never a browser the Markdown.

`test/llms.test.ts` holds it to the real docs: every page the sitemap lists
under `/docs` and `/reference` has a copy, every `llms.txt` link lands on a page
and an anchor that page has, every link into the repository is a file that is
there, and nothing from the site's chrome is in any file.

## Analytics

PostHog, started from `instrumentation-client.ts` and called through
`src/lib/analytics.ts`, which owns the list of events. Both
`NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN` and `NEXT_PUBLIC_POSTHOG_HOST` are optional:
with either unset analytics is off and nothing else changes, so nobody needs a
PostHog project to work on the site (`.env.example`). A production deploy
(`VERCEL_ENV=production`) refuses to build without them, which `next.config.ts`
enforces. `pnpm --filter website test` runs the tests in `website/test/`.

## Checking the built site

The pre-launch pass (SIG-273) is a script, so it can be run again:

```sh
pnpm --filter website build
pnpm --filter website start -p 3273
node scripts/check-pages.ts            # eight representative pages
node scripts/check-pages.ts --all      # every prerendered page, and the 404
node scripts/check-pages.ts --shots <dir>   # and a full-page PNG of each
```

It drives the Chrome that is installed (`CHROME` names another) over the
DevTools protocol with Node's own `WebSocket` (`scripts/lib/chrome.ts`), so it
needs no Playwright. At 390, 768 and 1280px it fails on sideways scroll, on
landmarks (one banner, main and contentinfo, every `nav` labelled), on a first
tab stop that is not the skip link, on any tab stop without the 2px `link` ring
or with the ring cut off by an ancestor's `overflow`, on a control without a
name, on a touch target under 44px at 390px, and on anything still moving under
`prefers-reduced-motion: reduce`. `test/launch.test.ts` holds what of the same
list is true of the source. Screenshots are for looking at, not for committing.

Lighthouse is not a dependency; run it with `npx`:

```sh
npx lighthouse@13.6.0 http://localhost:3273/ --chrome-flags="--headless=new"
```

Its SEO score is 66 on `localhost`, and that is the site working: `robots.txt`
disallows every host but the production one (`src/proxy.ts`). To score SEO as
production would, the request has to arrive as `https://ttylabs.dev`, and `.dev`
is HSTS-preloaded, so plain HTTP will not do. A local HTTPS proxy with a
self-signed certificate, forwarding to port 3273 with `Host: ttylabs.dev`, and a
Chrome started with `--ignore-certificate-errors` and
`--host-resolver-rules="MAP ttylabs.dev:443 127.0.0.1:<proxy port>"` does it;
pass that Chrome to Lighthouse with `--port`.

Decisions the pass made, so they are not undone:

- **The focus ring is `:where(:focus-visible)`, not a list of elements.** Chrome
  makes a box that scrolls focusable without a `tabindex`, and the list left the
  tables' scroll wrappers the browser's own 1px ring. Anything flush with the edge
  of a box that clips it -- a code block's body, a tab panel, a segment of the
  family filter, a search result -- draws the ring inside itself with
  `-outline-offset-2`, and the sidebar and the rail carry 4px of padding and
  `scroll-py-2` for the same reason.
- **A control smaller than 44px gets a bigger target than it is drawn.** An
  absolutely positioned `::after` grows a Copy button, a tab or the header's
  lockup into the padding around it, so the design does not move. Where there is
  no padding to grow into -- the title-bar install tabs, the search button -- it
  grows on `pointer-coarse`. The checker measures the `::after` as well.
- **Reduced motion stops every transition and animation**, in one block in
  `globals.css`, rather than picking through which of them count as motion.
- **Only the weights a page draws ship.** Every face is preloaded on every page,
  so a weight nothing uses is a request every visitor pays for. Barlow is 600
  alone: reading `document.fonts` after loading every page found 500 and 700
  drawn nowhere.
- **The CLI hero's text comes first in the source**, with `flex-row-reverse`
  putting the terminal on the left on a wide screen, so a phone, a screen reader
  and the Tab key all meet its heading before its terminal.
